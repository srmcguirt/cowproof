# Security review, 2026-10-13

An adversarial read of what merged on 2026-10-13 (`git log --oneline 8810c6f~1..HEAD`, twelve commits, HEAD `f585e79`): the yarn and pnpm fetch, the Bundler fetch, per-check time limits, platform-tagged port fixtures and the adapter pins, the trace totals (`rereadRate`, `CTX-SAVED`, the builder-written label) and the restored stdio tests. Nothing in the product was changed. Every finding has a file, a function, a concrete attack, a fix and a confidence; where a test could prove it, an `#[ignore]`d test fails today (see "Proofs").

Two audiences were attacked. **Builders as attackers:** a lane's patch, tree, lockfiles, fixtures, trace files and check output are hostile. **Directors and users as victims:** a human at a terminal, and an agent director reading tool output and MCP replies.

Severity: **P0** the verdict can be forged or a credential or host file leaves the machine; **P1** a sandbox or trust boundary is crossed with a precondition; **P2** a real attack on the director's machine, terminal, context or on the proof's meaning, limited by a precondition; **P3** hardening, or an attack that needs a trusted input to be hostile. Confidence is 1 to 10.

## S-1 (P2): builder text reaches the terminal and the agent unescaped

**Where.** `crates/cowproof-run/src/deps.rs:1633` `first_error_line`, used by `npm_failure` (1650), `yarn_failure` (1656), `gem_failure` (1662), `bundle_failure` (1669, public) and `pnpm_failure` (1684). It trims, takes the first matching line, cuts to 300 characters and keeps every control character. Sinks, all raw:

- `crates/cowproof-prove/src/runner.rs:915` puts `bundle_failure(output)` into the setup failure, and `crates/cowproof-cli/src/verify.rs:584` prints it: `println!("setup: {why}")`.
- `crates/cowproof-cli/src/verify.rs:479`, `:527`, `:596`: `eprintln!("infrastructure: {why}")` with `dependency fetch failed: ...` (the npm, yarn, pnpm or gem line) or `check <id>: ...`.
- `crates/cowproof-cli/src/verify.rs:578`: `println!("port: {failure}")`. The judge (`crates/cowproof-prove/src/port.rs:545`) builds each failure from `outcome.tool` and `outcome.id`, which are the strings a lane-written fixture file holds. `first_line` (`port.rs:387`) strips control characters from the error text only.

**Attack.** The verifier runs `bundle install --local` on the lane's `Gemfile`, which is Ruby. A `Gemfile` that does `puts "\e[2J\e[1;1H<forged text>\e]52;c;<base64>\a"` and then `raise` makes that line the first line of Bundler's output (real `bundle` 1.17.2 on this machine prints a `raise` message as ``[!] There was an error parsing `Gemfile`: <message>``, and `puts` output comes first). `bundle_failure` returns it with the escapes. A lane that is refuted anyway therefore chooses 300 characters printed in the director's terminal: clear the screen and print a believable `reproduced`, write the clipboard (OSC 52), set the title, or, for an agent director reading the Bash result, plant instruction text on a line that no label marks as builder-written. A fixture whose `id` holds the same bytes does it through the port failure line. The exit code (2) stays honest.

`cowproof run` is not affected: its verdict line and notes go through `one_line` (`crates/cowproof-cli/src/run.rs:4611`, `:4846`, `:4858`). `cowproof verify` has no such step.

**Fix.** Drop control characters in `first_error_line` (as `first_line` does) and print every lane- or tool-derived string in `verify.rs` through `one_line`, or move `one_line` to `cowproof_core` and use it in both. Prefix lines that come from lane code with a label (`builder-written:`), the way `escalations` does. Escape the `tool` and `id` in the judge's failure lines.

**Confidence 9.** Proofs: `audit_s1_a_gemfile_error_reaches_the_directors_terminal_with_its_escape_sequences` and `audit_s1_a_fixture_id_with_escape_sequences_reaches_the_port_failure_line`.

## S-2 (P2): one lane-added fixture hides a platform gap

**Where.** `crates/cowproof-prove/src/port.rs:584-605` (the coverage loop at the end of `judge`) and `crates/portkit/port/src/replay.rs:151` `ReplayReport::platform_gaps`.

**Attack.** The base holds `t/1@macos.json`, captured on macOS. The verifier runs on Linux, so the replay skips it and counts it in `other_platform`. The lane adds an untagged `t/lane-own.json` whose `expected` is whatever its port prints. Both `platform_gaps()` and the judge's loop mark tool `t` as covered because one outcome (the lane's own) ran on this platform, so no failure is raised. The port of `t` is proved on a platform where no reference-captured fixture of it was replayed, which is the case the new rule says must fail ("a port is never proved on a platform it was not captured on"). Before platform tags, the base fixtures replayed everywhere and an added fixture could only add checks.

A tool with director-captured held-out cases is still checked by those (they are captured live on the verifier's platform); the hole is the visible fixtures, and a packet without held-out cases is allowed.

**Fix.** Count coverage only from fixtures of the base: pass the base's `(tool, id, platform)` set to `judge` and require, per tool in `port.tools`, at least one base fixture that runs here. Lane-added fixtures keep being replayed and judged; they just do not count as coverage. Do the same in `platform_gaps` by telling the replay which fixture files the director vouches for.

**Confidence 8.** Proof: `audit_s2_a_lane_added_fixture_hides_a_tool_that_the_base_only_covers_for_the_other_platform`.

## S-3 (P2): remotes x specs

**Where.** `crates/cowproof-run/src/bundler.rs:422-426` (`plan`: `downloads.entry(spec).or_insert_with(|| source.remotes.clone())`) and `crates/cowproof-run/src/deps.rs:1488-1495` (`gem_fetch_script` writes one `--source '<remote>'` per remote per gem). `plan` runs at least three times per fetch (`Needs::of`, `unfetched_notes`, `fetch_bundler`, deps.rs:541, 579, 1524), each after a full `parse`.

**Attack.** A `GEM` section may list any number of `remote:` lines, and every spec in it is given a copy of all of them. A lockfile of 2 005 lines (about 45 KB) makes the plan hold 1 000 000 remote strings; about 1 MB (20 000 remotes, 30 000 specs) holds 600 million, tens of gigabytes. Every remote is a valid https URL, so no check rejects it, and `capture_patch` (`crates/cowproof-cli/src/run.rs:2918`) puts no limit on the patch. The director's `cowproof run` (at lane end) or `cowproof verify` is killed for memory, and so may other processes on the machine. The script, were it reached, would be the same size again.

**Fix.** Keep remotes once per source (an index into `lock.sources`) and emit the `--source` list once per source group; cap remotes per source (8 is plenty), specs, and the lockfile's size (say 8 MiB) in `gem_lock` before `parse`; make `gem_plan` run once and pass its result along.

**Confidence 9.** Proof: `audit_s3_the_bundler_plan_multiplies_remotes_by_specs`.

## S-4 (P3): quoted `.npmrc` keys keep their token

**Where.** `crates/cowproof-run/src/deps.rs:667` `strip_npmrc_auth`, key test at `:688`.

**Attack.** `ini` (npm's and pnpm's parser, checked against the copy bundled with npm 11.19) unquotes keys: `"//registry.npmjs.org/:_authToken"=T` and `'//host/:_authToken'=T` both set the token. The stripper takes the text after the last `:`, `_authToken"`, which matches no key, so the line is kept and the fetch gets a credential. The entry's cache, which the verifier mounts read-only into tests, can then hold it. The input is the base's `.npmrc`, so this is accidental exposure of a director's own token, not a lane attack (hence P3). The same holds for tokens in a URL query or path (`registry=https://host/?token=...`, also `npmRegistryServer` in `.yarnrc.yml`), which only the `user:pass@` form of `drop_url_credentials` handles. The Yarn side is stronger: its word list catches `'npmAuthToken'` in single quotes, and only an escape such as `"npm\x41uthToken"` slips through.

**Fix.** Unquote the key (JSON or single quotes) before the comparison, as `ini` does, and drop any value of a key containing `token`, `auth`, `password`, `secret` or `key` after the last `:`. Tell the director in the capsule note when a query string was left in a registry URL.

**Confidence 8.** Proof: `audit_s4_a_quoted_npmrc_key_keeps_its_token`.

## S-5 (P3): a builder can blind `watch` to the credential column

**Where.** `crates/cowproof-report/src/traces.rs:152-176` (`trace_totals` keys `by_tool` by `record.tool`, with no cap on count or length), `crates/cowproof-cli/src/run.rs:4263` (the totals go whole into `run.json`), `crates/cowproof-cli/src/watch.rs:367-376` (`read_run_json` returns nothing above 4 MiB), used by `lane_credential` and `lane_ctx_saved`.

**Attack.** The builder writes `<lane>/portkit/traces/x.jsonl` itself. One record whose `tool` is 5 MiB long (a trace line may be 32 MiB, `MAX_FILE_BYTES`) makes `byTool` and so `run.json` larger than 4 MiB. `lane_snapshots` then shows no CREDENTIAL cell and no CTX-SAVED for the lane: the signal that a credential was readable inside the lane (`credentialInLane`, D28 clause 6) disappears from `watch` and from the `lanes` tool without a word. The same walk reads every `*.jsonl` of a lane into memory at once (`records: Vec<CallRecord>`), so the 32 MiB bound is per file, not per lane. `get_lane_state` also reads `run.json` unbounded (a lane with a very large file costs every `lanes` poll up to three reads of it).

**Fix.** Cap `by_tool` at 64 names of 64 characters (fold the rest into `other`), cap the walk at one aggregate byte count and file count, and make `read_run_json` say `unreadable` (a `?` cell) instead of nothing when the file is too large.

**Confidence 8.** Proof: `audit_s5_a_builder_can_blind_watch_to_the_credential_column_by_growing_run_json` (the honest lane shows both columns; the bloated one shows none).

## S-6 (P3): the builder-written label stops at `run.json`

**Where.** `crates/cowproof-cli/src/run.rs:4265` writes `traceBuilderWritten: true` beside `traceTotals`; `crates/cowproof-cli/src/watch.rs:440-457` (`LaneSnapshot.ctx_saved_bytes`, served by the `lanes` tool, `director_tools.rs:296-318`), the `CTX-SAVED` header (`watch.rs:500`), `crates/cowproof-report/src/rollup.rs` `Delivered` and `LaneRow` (JSON), and `Capsule.trace_totals` (`capsule.json`) carry the same numbers with no marker. The rollup's text output has the label; its `--json` does not.

**Attack.** An agent director that calls `lanes` sees `"ctx_saved_bytes": 123456789` as if the runner had measured it; the builder chose it. The `escalations` tool shows the right pattern (`builder_written`, a notice, caps); `lanes` does not apply it to a number.

**Fix.** Name the field `ctx_saved_bytes_builder_reported` (or nest it under `builder_written`), add the notice to the `lanes` tool description, head the column `CTX-SAVED*`, and put `"builder_written": true` inside `TraceTotals` and the rollup's `delivered` rows.

**Confidence 8.** Proof: `audit_s6_the_lanes_tool_does_not_label_a_builder_reported_figure`.

## S-7 (P3): the cache key reads what no planner will

**Where.** `crates/cowproof-run/src/lib.rs:766-790` `dependency_cache_key` uses `Path::is_file` (which follows a symlink) and `fs::read` (whole file). `deps.rs:571` `is_regular` (no symlink) is what `Needs::of`, `js_plan`, `gem_lock`, `fetch_js` and `read_config` use. `Needs::of` still uses `tree.join("Cargo.lock").is_file()` (`deps.rs:541`).

**Attack.** A patch that makes `Gemfile.lock`, `yarn.lock`, `pnpm-lock.yaml` or `package.json` a symlink to a large file the director can read (a log, a disk image, a sparse file) makes the key function load it into memory; its contents change the key. The planners treat the file as absent, but `prefetch_in` computes the key whenever anything else in the tree needs fetching or earns a note (a real `Cargo.lock` is enough), and the key reads every lockfile name that `is_file` accepts. Together with S-3, every lane-written lockfile or manifest (`fs::read_to_string` in `js_plan` at deps.rs:497 and `gem_lock` at :619, `fs::copy` of `package.json` at :1367) is read with no size bound.

**Fix.** Use `symlink_metadata` in the key and refuse (not hash) a symlinked input; read through one helper that stops at a limit (8 MiB for lockfiles and manifests).

**Confidence 8.** Proof: `audit_s7_a_symlinked_lockfile_does_not_belong_in_the_cache_key`.

## S-8 (P3): environment failures refute the lane

**Where.** `crates/cowproof-prove/src/runner.rs:870-925` `bundler_setup`, `crates/cowproof-cli/src/run.rs:4576-4578` and `:5123-5137` (`Evidence.setup_failed` is a refutation: "The lane's own gems did not install, so it is refuted, not an infrastructure failure"). The program is `$COWPROOF_BUNDLE`, the first `bundle` on `PATH`, or the bare name run inside the sandbox.

**Attack.** Not a lane attack; a false verdict. `bundle` missing from the sandbox's `PATH`, a version-manager shim (`~/.rbenv/shims/bundle`) that needs a home the sandbox hides, a native extension that needs a compiler or header the sandbox lacks, a Ruby older than the lockfile's `RUBY VERSION`, or the 20 minute `BUNDLER_STEP_TIMEOUT` all end as exit 1 and a `refuted` lane. A fast path to dismiss good work, and a way for a hostile `Gemfile` (`sleep`) to turn a proof into a refutation of the director's own tooling.

**Fix.** Classify by cause: spawn failure, 126 and 127, a timeout and a signal are `infrastructure`; only a Bundler resolution error (`Could not find gem`, `Your bundle is locked to`) is the lane's.

**Confidence 6.** No proof test: `judge` is private and the step needs the sandbox and a Ruby. Settle it by running `cowproof verify` on a Bundler capsule with `COWPROOF_BUNDLE` unset and `bundle` off the `PATH`.

## S-9 (P3): gem integrity and source come from the lane

**Where.** `crates/cowproof-run/src/deps.rs:1599-1607` (checksum compared when the lane's lockfile gives one), `crates/cowproof-run/src/bundler.rs:383-426` `plan`, `crates/cowproof-run/src/fetch_proxy.rs:136` `bundler_from_tree` (host-level allowlist).

**Attack.** The fetch trusts the lane's `Gemfile.lock` for what to fetch, where from, and what it must hash to. A patch can (a) delete the `CHECKSUMS` section: a gem the base pinned is then downloaded unverified, and Bundler in the verifier (`BUNDLE_FROZEN`, local) has nothing to compare against; (b) move a gem the base takes from a private host (allowlisted because the base names it) to `https://rubygems.org/` (always allowlisted), a dependency-confusion step; (c) add a gem unknown to the base with no checksum. Third-party gem code then builds and runs inside the verifier's sandbox (`extconf.rb`, `Gemfile`), the same trust as the lane's own tests, so this is not an escape; it changes what the proof ran. npm has the same shape through `resolved` (not new).

**Fix.** Take checksums for every `(name, version, platform)` present in the base lockfile from the base; note, in the capsule, each gem whose checksum is absent; pin each base gem to its base remote and refuse a lane lockfile that moves it.

**Confidence 7.** No proof test (needs a network or a fake rubygems).

## Checked and found sound

**Fetch (yarn, pnpm, Bundler)**

- The allowlist of every ecosystem is built from the base only: `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `cowproof.toml` and the base's Bundler lockfile, restored by `RegistryConfigSnapshot` before the allowlist is read. A lane `remote:` or `registry` adds nothing (deps.rs:905-990, fetch_proxy.rs:135-190).
- `RegistryConfigSnapshot::restore` removes a patched symlink, directory or parent in the way without following it, including `.cowproof-base` (tests at deps.rs:2019-2112, 2875-2935). The base lockfile copy is not in the verifier's tree (the fetch has its own rebuilt tree, `crates/cowproof-cli/src/verify.rs:151-180`).
- Shell injection through a gem name, version, platform or remote: the reader allows only `[A-Za-z0-9._-]` (name not leading `-`, version leading digit), and every word is single-quoted. I ran a script of the same shape with a remote `https://a.example/'; touch ...; echo '`: it arrived as one argument and nothing ran.
- The lockfile reader fails closed (unknown section, merge marker, bad checksum, `GIT`, `PATH`, `PLUGIN SOURCE`, http remote without checksum). 1.2 million mutated inputs across the lockfile reader, `strip_npmrc_auth`, `strip_yarnrc` and `strip_yarnrc_yml` raised no panic.
- Platform matching is CPU and OS only, libc and macOS version ignored, everything else left out and named; a name and version with no variant for the host is `not_fetched`, not a half entry.
- `gem fetch` runs in a cleared environment with a private `HOME`, `GEM_HOME`, `GEM_PATH` and `GEM_SPEC_CACHE`, `--clear-sources`, and reads no `Gemfile` or `.bundle/config`; `bundle` is never run at fetch time. A remote with `user:pass@` has it removed before it reaches the command line (deps.rs:1479-1500).
- yarn: `yarnPath`, `yarn-path` and `plugins` (and the lines under them) are dropped; the four Berry credential names are caught whole-line even when quoted or in a flow mapping; block scalars under a credential key go with it; `YARN_ENABLE_SCRIPTS=false`, `--ignore-scripts` / `--mode=skip-build` are set; pnpm runs with `--ignore-scripts` and `manage-package-manager-versions=false`. Lockfiles and manifests are read as regular files only (`is_regular`).
- Fetch results appear in the cache by one rename after success; an interrupted fetch leaves no entry; entries and their walks never follow a symlink (`crates/cowproof-run/src/cache.rs`).
- Verifier: the entry's `bundler/cache` is mounted read-only, `link_vendor_cache` replaces a `vendor` symlink or file and a `vendor/cache` directory without writing through them, `BUNDLE_IGNORE_CONFIG`, `BUNDLE_APP_CONFIG` and `BUNDLE_USER_HOME` are fixed so a tree's `.bundle/config` cannot redirect Bundler, and the install path lives in the verifier's cleared scratch. `NPM_VERIFIER_ENV` sets offline and no-scripts for npm, Berry and classic; the cache variables point at the read-only entry.
- A cache key covers the target, every lockfile, every registry config and (for a JavaScript lockfile) `package.json`, with names and lengths, so bytes cannot move between files.

**Time limits**

- `parse_check_timeout`: digits only, `s` or `m` or an integer, `checked_mul`, 1 s to 6 h; floats, negatives, signs, spaces, `1h`, `0` refused. `invalid-check-timeout` lints it; `run` refuses a header that fails (`header.check_limit_error()`); a redirect packet is linted before it replaces the checks.
- `refuse_limit_mismatch` runs before anything is built, range-checks every recorded `timeout_ms`, and requires the recorded limit to equal the last header's. A capsule's check files are sealed, so a recorded limit cannot be changed after the fact. A capsule with no packet versions still cannot ask for more than 6 h per attempt (an old capsule, or one whose header does not parse, is replayed under what it records).
- `host-agent check` accepts 1 s to 6 h, still refuses an empty or NUL command and a bad port block; the limit comes from the director's header, not from the builder.

**Port**

- A tagged fixture must carry an id that ends `@<platform>`, and a fixture that disagrees fails the whole load, never a silent skip. The judge counts other-platform fixtures from the files and compares the replay's count, rejects an outcome for a fixture the host does not replay, and `fixture_findings` now includes `platform`, so retagging, deleting or moving a base fixture (also through a symlink, which the judge cannot see) is a finding.
- `env`, `normalized` and `expect_error` are not in the base-fixture guard; I read `replay_one` and found no way for a lane to turn a failure into a pass through them (`normalized` can only add a check, `expect_error` compares the port's failure with the recorded error, `env` is not used on replay). Not tested with a process-wrapped port.
- The adapter pins read nothing from the tree, and apply only when `PORTKIT_NOW` or `PORTKIT_SEED` are set by the director; the two adapters draw the same bytes for the same seed; seeds are integer-checked. The numpy pin imports `numpy` through the adapter's own `sys.path`.
- `port-no-base-fixtures` reads the base through `git ls-tree HEAD -- <dir>`, the held-out file only through the validated id store or an explicit path outside the repository (`..` refused), and can only turn an error into a warning for a tool the director's own cases name.

**Trace totals and the director's tools**

- `Summary::add` and `trace_totals` saturate; `u64::MAX` produces `18.4E`, `saved_bytes` floors at zero, `rereadRate` is 0 to 1 or null and the rollup drops anything outside it. The trace walk follows no symlink at any step and skips files over 32 MiB.
- `watch` prints only runner-owned or alphabet-limited strings: ids, verdict and credential labels (`[a-z-]`, 32 characters), counts, ages and the new `CTX-SAVED` number. Event summaries hold ids, flags and sizes, never builder words. `read_run_json` does not follow a link.
- The `escalations` tool wraps every builder string in `builder_written`, caps the question at 4000 bytes, other fields at 2000, ten `tried`, six options, 64 KiB in all, and `Ask.kind` is an enum. `lanes` returns numbers and enums. A lane id cannot leave the lanes root.

**Tests**

- The restored stdio and `pk` tests call no `set_var`, give every `pk` a throwaway `HOME` under `/var/tmp`, and stop processes by pid through the shared helper (no `kill` binary).

## Unconfirmed

- **Corepack shim as the host's `yarn` or `pnpm`.** `package.json`'s `packageManager` is lane-written; with corepack enabled the shim downloads that version from `registry.npmjs.org` (allowlisted) and runs it. Settle it by `corepack enable` on a test machine, then a fetch of a tree whose `packageManager` names an old version, and read `argv.txt`/the proxy log.
- **Yarn Berry workspace scripts under `--mode=skip-build`.** Berry's docs say `enableScripts: false` still runs workspace scripts; `--mode=skip-build` and `YARN_ENABLE_SCRIPTS=false` are both set and should cover it. `yarn` is not installed here. Settle it with a real Berry install of a tree whose root has `postinstall: touch marker`.
- **`exec:`, `portal:` and `link:` entries with absolute paths in `yarn.lock` and `pnpm-lock.yaml`** copy or link host files into the entry, and a Berry `exec:` runs a Node script it can read. The project directory holds only the manifest and lockfile, and the work path embeds a pid and a nanosecond stamp the lane cannot know, so I found no way to run lane code; a host file can reach the entry, and from there the checks. Settle it with a lockfile `link:/etc/hosts` and look at the entry.
- **TOCTOU in `read_lane_traces`.** It tests `file_type()` and then opens by name; a process of the builder that survived the group kill could swap a file for a FIFO and hang the director at lane end. I did not build the race.
- **`Fixture::path_within` joins `tool` and `id` unchecked** (`crates/portkit/port/src/fixture.rs:164`). Safe while every cases file is the director's or the capture runs in the capture sandbox; unsafe if a lane-written cases file ever reaches a capture outside it. Settle it by tracing `port.cases` for a visible-fixture capture by the director.
- **A committed `vendor/cache` and the cache key.** The key does not include whether `vendor/cache` exists, so a tree with one (not fetched, per `gem_plan`) and a tree without it share an entry; the verifier mounts the entry whenever it has a Bundler part and replaces the committed directory, while the capsule says bundler was not fetched. Same lockfile bytes, same gems, so I rate it a determinism note. Settle it with two lanes of one Gemfile.lock.
- **`first_error_line` on npm, yarn and pnpm errors** carries a lane string only if the tool echoes one; npm percent-encodes a URL, so I could not make a real npm print an escape. Fixed anyway by S-1.
