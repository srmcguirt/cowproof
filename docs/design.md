# Design: cowproof

Generated by /office-hours on 2026-10-09

Mode: Builder

## Problem Statement

Running many AI coding workers in parallel on one project is now easy. Trusting what they hand back is not. Cheap workers game their checks: they delete assertions and keep the test names, write always-true security policies, swallow their own exceptions, or report deferred work as done. A director agent that reads every diff becomes the bottleneck, and one that doesn't read them lets that work land.

The founder has run hundreds of lanes on the Everydom platform with a home-grown runner (`scripts/lanes/` in that repo, plus six Rust crates in the private `Everydom/lanes`) and three director skills (`lane-dispatch`, `lane-handback`, `lane-escalate`). It works, but it is Everydom-specific, needs Node and Rust, and its escalation path is a one-way question file. cowproof rebuilds it as an MIT tool that the founder's own projects and outside users can run.

Target shape, in the founder's words: "I'm imagining having opus running the build direction with haiku builder. Haiku escalates the problem as a message back to the director, for direction. Director escalates to another agent or directs with solution/answer to question."

## What Makes This Cool

- **The work comes back as a proof, not a claim.** Each lane returns a proof capsule: base revision, patch hash, checks re-run by a verifier the builder never controlled, held-out check results, gate results and the escalation log. Any machine (CI, a reviewer, the founder's next project) can replay it.
- **Cheap builders, expensive judgment, spent only where it matters.** Haiku does the token-heavy work. Opus spends tokens on rulings and on the exceptions the gates surface, never on routine diffs.
- **The name does the explaining.** Every lane runs on a copy-on-write (COW) clone, the work must come back proven, and the real tree is cow-proof: builders graze in their own clones and cannot trample it.

## Constraints

- MIT, developed in the open on `srmcguirt/cowproof` (public since 2026-10-09). Fresh git history: the `Everydom/lanes` history holds a host inventory, private paths and project packets, so code is copied in, never its history.
- **Provenance.** The lane crates, runner and skills come from Everydom (`Everydom/lanes`, `Everydom/platform`). The owner authorized their release under MIT on 2026-10-09; the record and its exact scope are in [provenance.md](provenance.md). Real product material (lane patches of product code, real packets, host inventories) stays out even when it sits beside covered code.
- **Scrub check before every push.** `scripts/scrub-check` (and the same check in CI) fails on: absolute home paths, host and tailnet names, private repository names other than in attribution, email addresses, and any secret pattern `gstack-redact` reports at HIGH or MEDIUM. It covers code, fixtures, `flaws.toml` and skills, not just docs.
- One install for outside users: one package that installs the `cowproof` binary and its `pk` and `pk-read` companions. No Node requirement for users; Node is needed only by the director to recapture parity fixtures from the reference runner.
- The runner never writes to the real tree. Every applied change goes through the director. Handoffs reach the real tree only as part of a lane's patch, which the director applies.
- Every role (director, builder, ladder, challenger) is configuration. Codex and OpenRouter builders keep working.
- Two auth modes ship in the first release (founder decision, 2026-10-09): Anthropic API key, documented as the supported path, and Claude subscription, documented as experimental and subject to the user's own plan terms until Open Question 2 is settled. cowproof never runs a login flow, stores a token or pools a subscription.
- Cost figures from Claude Code are client-side estimates (`total_cost_usd`, per the headless docs); cowproof labels them as estimates everywhere.
- macOS (sandbox-exec, APFS clonefile) and Linux (bubblewrap, reflink) from the first release; Windows through WSL only. **Fail closed:** if the sandbox cannot start (no unprivileged user namespaces, sandbox-exec removed or refusing), the lane does not run. `--unsandboxed` exists for trusted local experiments only, and marks the lane and its capsule `unsandboxed` everywhere they appear.
- portkit is part of cowproof (founder decision, 2026-10-09): its crates move into this workspace and ship in the one binary. It is not an optional external tool.
- **The porting harness is polyglot** (founder decision, 2026-10-09). Scripts in any source language port to Rust through the same capture, replay and proof process: Python, Node/TypeScript and shell first, through per-language capture adapters, with the adapter model open to others.
- Everydom keeps its current runner until cowproof has run real waves.

## Premises

1. **The director's attention is the bottleneck, not compute.** Mechanical proof gates carry most review; the director reads gate reports, exceptions and escalations, not diffs. (agreed)
2. **Haiku is the default builder; escalation is the safety net.** Revised by the founder, who rejected a model bake-off before launch: "Escalation is the net." Escalation therefore has to be cheap and early. A builder must escalate after a bounded number of failed attempts on the same check or past a share of its cost cap, rather than thrash. Escalation and reassign rates are measured in production. (agreed as revised)
3. **Outside users need one installable binary.** The runner's Rust port, proven with portkit parity fixtures, moves into the first release instead of a late phase. (agreed)
4. **The novel part is escalation plus proof, not parallel lanes.** COW worktrees and parallel agents are common (`lukeed/lane`, `simgit`, `git-cow`, Vibe Kanban, Conductor, Claude Code subagents). The escalation protocol and the proof gates ship first and best; remote hosts and plan files follow. (agreed)

## Cross-Model Perspective

Codex (gpt-6-luna, cold read of a structured summary, 2026-10-09):

- Coolest version: "Make every lane return a *proof capsule* a CI system can replay: the base revision and patch hash, the checks run by a trusted verifier, their results, and the escalation decisions that shaped the work. That turns 'the builder says it passed' into a reviewable artifact another machine can check."
- What excites the founder: the director-builder exchange and changing course mid-task.
- Halfway there: Vibe Kanban for managing agents, `lukeed/lane` for clone-and-run. Director's note: the founder's own runner is the real existing half; it already does clones, sandbox, slots and diagnostics.
- First build: one end-to-end escalation-and-proof slice in a Rust binary, Claude CLI only, synthetic task. "That tests the project's defining promise before spending the weekend porting every runner feature."

Adopted: the proof capsule, and the slice-first order. No premise was challenged.

## Approaches Considered

### Approach A: Extract and scrub
Move the Node runner, crates and skills over as they are. Ruled out: two runtimes for outside users and no differentiator at launch (breaks premises 3 and 4).

### Approach B: Escalation-and-proof slice first, then fold the runner in
Chosen. See Recommended Approach.

### Approach C: Protocol first
Publish the packet, escalation and capsule formats as a spec with a thin reference CLI. Ruled out: high adoption risk, and the founder's platforms need the full runner anyway.

## Recommended Approach

**Approach B.** Build a Rust `cowproof` binary that runs one loop end to end, then port the existing runner's features into it, each proven against the Node original with portkit parity fixtures.

### Roles

| Role | Default | Job |
| --- | --- | --- |
| Director | Opus, in the user's Claude Code session | Writes packets, rules on escalations, judges exceptions, applies, gates, commits |
| Builder | Haiku 4.5 through headless Claude Code | Implements one packet inside its lane |
| Ladder | Sonnet, then Opus | Takes over a lane the director reassigns |
| Challenger | a different model family where available | Attacks a design ruling or a packet's checks |

Codex CLI and OpenRouter (opencode) builders remain supported.

### Lifecycle

```
packet -> lint -> preflight -> dispatch -> run <-> escalate -> handback -> verify -> gates -> capsule -> director -> apply, gate, commit
```

- **Packet**: two files. `packet.md` is what the builder sees: a JSON header (id, `owns` globs, command allowlist, declared `checks` with ids, role, model, timeout, cost cap, resource class, `appendOnly` guards, protected paths) and the task text. `packet.heldout.toml` holds the held-out checks; it lives only in the lane's control directory (see Trust boundaries) and is never placed in the clone, the builder prompt or any path the sandbox can read. Reuses `lanes-core` parsing.
- **Lint**: refuses packets with masked pipe statuses, missing check paths, secret references, or ids reserved twice in a plan. Reuses `lanes-lint`.
- **Preflight**: a cheap adversarial pass tries to satisfy the packet's visible checks by cheating (stubbing, deleting assertions, hard-coding outputs). If a cheat passes, the checks go back to the director. Idea from SpecGuard (arXiv 2610.09159) and GraderGuard. Not in the first slice.
- **Dispatch**: requires a committed base by default. With `--allow-dirty`, the uncommitted diff is recorded as a base patch and travels in the capsule, so the base can be rebuilt as commit plus base patch. Then: COW clone (APFS clonefile, reflink, copy fallback), OS sandbox (fail closed), lane-private HOME and Claude config directory, port block, scratch directory, machine-wide class slots, disk floor. Ported from `run-lane.mjs`.
- **Run and escalate**: see the escalation protocol.
- **Handback**: in-scope patch (including the handoff the builder writes in the clone), outside-ownership patch (kept, never applied). The runner, not the builder, writes `summary.json`, `escalations.jsonl` and the trace rollup, into the control directory.
- **Verify**: see Verifier.
- **Gates**: mechanical checks over the patch and the verifier's results (see Proof gates).
- **Capsule**: everything needed to replay, sealed into one bundle (see Proof capsule).
- **Director**: reads the gate report, open escalations, the handoff's limits and questions, and greps the patch only where a gate points.
- **Apply**: the director applies the patch with a three-way apply. If the real head has not changed any file the patch touches since the base, the capsule records `applied-clean` plus the director's gate run. Otherwise `cowproof prove --at HEAD` re-runs the verifier on the applied tree and appends an `applied-at` record; a lane is proven only at the tree where it was proven.

### Lane states

`queued`, `running`, `parked` (waiting on a ruling), `stalled` (idle past its class threshold), `finished` (handback written, not yet verified), `proved` (verifier and gates passed), `refuted` (a gate or the verifier failed), `escalation-limit`, `stopped`, and the existing runner failure classes (`timeout`, `cost-cap`, `worker-*`, `sandbox-unavailable`, `runner-error`).

### Escalation protocol

The builder gets three tools, `ask`, `check_ruling` and `run_check`, mirrored as `cowproof ask`, `cowproof ruling` and `cowproof check <id>` for runtimes without MCP. The tool process inside the sandbox is only a client: it passes requests over a socket to the runner, which runs outside the sandbox and alone owns the queue, the rulings and the lane records. An `ask` looks like this:

```json
{
  "kind": "blocker | design | scope | environment",
  "question": "one paragraph",
  "tried": ["what was attempted and what happened"],
  "options": [{ "id": "a", "summary": "...", "cost": "..." }],
  "recommend": "a",
  "blocking": true
}
```

**How a ruling reaches the builder.** No tool call is held open waiting for the director, so no runtime tool timeout applies.

- `blocking: true`: `ask` returns at once with "parked", and the runner ends the session itself (the same way it ends one for a forced escalation), so the builder cannot keep working after it parks. The runner records the session id from the stream. When the director rules, the runner resumes that session with the ruling as the next user message (`claude -p --resume <session-id>` for Claude builders). Codex and opencode builders use their own resume command where one exists; where none does, a blocking escalation can only be answered by `reassign` or `stop`, and the runtime adapter says so. Parked time is paused against the lane timeout.
- `blocking: false`: `ask` returns at once and the builder keeps working. It calls `check_ruling` between steps; for Claude builders the runner also attaches any pending ruling as added context through the lane's tool hook, where the runtime supports hook context.
- **Cost of a park.** A resume after the provider's prompt cache has expired re-reads the session context at full input price. The runner records parked time and the resumed turn's input tokens, so the cost of slow rulings shows up in the capsule and the watch view. The default park limit is 30 minutes.

**Escalate early: detection and enforcement.**

- Checks are declared in the packet with ids. Builders run them through `run_check <id>`. The runner treats the check as untrusted code: it runs it in a fresh sandbox with the lane's filesystem policy or stricter (write access to the clone and scratch only, nothing in `lane/control/` or the real tree readable, no credentials, no network) and records only the exit status it observes and the attempt count. For Claude builders, the lane's tool hook also matches Bash commands against declared check commands, so a check run directly still counts.
- "The same check failed twice" means two recorded failures of one check id with no pass in between.
- Cost is tallied from the builder's event stream as turns complete (usage per message where the runtime reports it). Where a runtime reports cost only at the end, the cost trigger is replaced by a turn budget (`--max-turns` for Claude).
- On a trigger, the runner ends the session and opens a forced escalation itself, filled with the failing check's output and the attempt history. Forced escalations count toward the per-lane limit.
- Limits per lane: 3 escalations (forced ones included) and 30 minutes parked by default. Beyond either, the lane ends as `escalation-limit` with its work kept. After a `reassign`, the attempt counters reset; the escalation count does not.

Escalations land in a runner-owned queue in the control directory, so they survive restarts and work for every runtime. The director follows one stream, `cowproof watch --events`, which a Claude Code Monitor can tail, and rules with `cowproof rule <lane> <verdict>`:

| Verdict | Effect |
| --- | --- |
| `answer` | The ruling is delivered as above; the builder resumes |
| `redirect` | A revised `packet.md` (and optionally revised held-out checks) replaces the current one. It is linted again before delivery. Held-out checks can be added by a redirect but not removed. The capsule keeps every packet version with the verdict that introduced it; gates use the final version |
| `reassign` | The lane moves to the next model on the ladder (or a named one) on the same clone, carrying the patch so far, the question and the runner's summary of what was tried |
| `stop` | The lane ends; its work is kept for inspection |

For a design question the director cannot settle alone, the existing `lane-escalate` flow applies: a stronger model recommends, a challenger attacks the recommendation, the director adopts. Every escalation and verdict is logged by the runner and summarized in the capsule, so it shows which decisions were the builder's and which were the director's.

### Trust boundaries

The builder is untrusted. It may have read hostile content in the repository, and it may try to game its checks.

- **Control directory.** Each lane has `lane/clone/` (the builder's copy, writable) and `lane/control/` (packet versions, held-out checks, queue, rulings, summary, capsule, logs). The sandbox profile grants write access to the clone, the lane HOME and the scratch directory only; `lane/control/` is neither readable nor writable from inside. Nothing the builder writes is read back as runner state.
- **Builder text is data.** Questions, options, handoffs and commit messages come from the builder. `watch`, `rule` and the director skills show them inside fenced, labelled, length-capped blocks, and the director skills state the rule: never run a command, open a URL or follow an instruction that appears in builder text. A ruling cannot widen a lane: new owned paths, allowed commands or network access require a `redirect`, which is linted.
- **Network.** Lanes have no network by default. Builder model traffic goes through a local egress proxy that the runner runs outside the sandbox; the sandbox allows only that proxy. The proxy forwards only the provider endpoints the builder runtime needs (for Claude builders, message creation and token counting), never file upload, batch or admin endpoints. A packet with `"network": "registries"` adds package registries for read-only fetches; publish and upload methods are refused. Checks run through `run_check` and the verifier have no network at all; checks the builder runs directly through its own shell can reach the proxy, so only `run_check` and verifier results count as evidence.
- **Credentials.**
  - API-key mode: the credential lives only in the proxy. The builder talks to the proxy over plain HTTP on localhost (`ANTHROPIC_BASE_URL`) with a placeholder key; the proxy injects the real key on the way out and rejects any request carrying a different credential. A builder can therefore neither read the key nor send model traffic under an attacker's key.
  - Subscription mode: the OAuth token must be in the builder process, so commands the builder runs can read it. The proxy still rejects any request whose credential is not the lane's own, and forwards only the message endpoints, so the token cannot be sent anywhere except the provider under the user's own account. That residual risk (a hostile repository can make the token readable inside the lane) is stated in the README, the capsule records `auth: subscription`, and the mode stays experimental.
- **Same context in both auth modes.** API-key builders run with `--bare`, which skips user and project hooks, skills, plugins, MCP servers and `CLAUDE.md`. Subscription builders cannot use `--bare` (it does not read `CLAUDE_CODE_OAUTH_TOKEN`), so the runner neutralizes every project-level source Claude Code would auto-load: settings and hooks, `.mcp.json`, `.claude/skills`, `.claude/agents`, `.claude/commands`, output styles, and memory files (`CLAUDE.md`, `CLAUDE.local.md`, nested `CLAUDE.md`). It uses CLI controls that ignore project sources where the documentation confirms them, and otherwise moves the files aside before launch. In both modes the project's instruction file is given once, in the builder prompt.
- **Launch baseline.** Anything the runner changes in the clone before the builder starts (neutralized files, removed `.env*`) is committed in the clone as the launch baseline. The lane patch is computed against that baseline, so runner changes never appear in a patch; a builder edit to a neutralized path is reported separately and fails the protected-path gate.

### Verifier

- The verifier builds a fresh clone of the base (commit plus base patch), applies the lane patch, and runs the packet's visible checks and then the held-out checks, inside a sandbox with no network and no credentials. It runs as a separate process the builder never started.
- **The patch cannot quietly change what the checks run or what the gates look for.** Gates load the flaw packs and all gate configuration from the base revision, never from the patched tree. Check and gate infrastructure is protected by default: test configuration, build scripts, package manifests and their scripts, CI files, `cowproof.toml`, `cowproof/**`, every path named in `[proof] packs`, and any file a declared check command references. A patch that touches one fails the protected-path gate unless the packet owns that path explicitly, and then the gate still reports "check harness changed" for the director.
- Held-out checks are copied in from the control directory at verify time, so their files are never in the builder's clone. Held-out checks are written per packet and never reused, so a shared capsule cannot leak them to a later builder.
- An `--unsandboxed` lane can reach `finished` but never `proved`; the verifier always runs sandboxed.
- The builder's own reported results are informational only.

### Proof gates

| Gate | Catches | Source |
| --- | --- | --- |
| Ownership | changes outside `owns` | exists |
| Append-only | deleted assertions, emptied test files | exists |
| Protected paths | edits to tests, fixtures or policies the packet must not touch | new |
| Verifier re-run | checks the builder claimed but that fail when run independently | new |
| Held-out checks | work that satisfies only the visible checks (idea: EvilGenie, SpecBench). A packet without held-out checks gets a warning, not a failure, unless the repository sets `require_heldout = true` | new |
| Flaw rules | known gaming patterns: swallowed exceptions in assertions, always-true policies, test-only code in production paths, secrets in URLs | exists as `lanes-report` `flaws.toml`; split into a generic pack and project packs |
| Claimed vs. run | handoff checks the verifier never saw | exists in part |

A gate verdict is a triage signal; the director still rules. Each new flaw found at handback becomes a rule.

### Proof capsule

A capsule is a directory (or a `.capsule.tar.zst` of it) in the control directory, holding everything a replay needs, not just hashes:

- `capsule.json`: base commit, the remote it is reachable from, base tree hash; hashes of every file below; environment fingerprint (OS, architecture, toolchain versions the checks use); lane state; builder model per segment (a reassigned lane has several), auth mode, estimated cost and tokens, parked time, portkit trace totals
- `base.patch` (only when dispatched with `--allow-dirty`) and `lane.patch`
- `packets/`: every packet version with the verdict that introduced it, and the held-out checks (secret only while the lane runs; a replayer needs them)
- `checks/`: per check id, the command, exit status, attempt count, duration and output hash from the verifier
- `gates.json` and `escalations.jsonl`
- `applied/`: any `applied-clean` or `applied-at` records

`cowproof verify <capsule>` rebuilds the base, applies `lane.patch`, re-runs every check in the same sandbox and network policy, and compares **pass or fail per check id**. Durations and output hashes are recorded but never compared, because they vary between runs. A check marked `flaky` in the packet is retried up to three times. If the base commit is not reachable from a remote, the capsule is marked `local-replay-only`. Signing comes later.

### portkit integration

portkit (`pk`, the founder's Rust CLI, public at `srmcguirt/portkit`, MIT or Apache-2.0) ports scripts to Rust CLI tools with a parity harness and measures agent tool usage through hooks. **It moves into this workspace** (founder decision, 2026-10-09). The full plan, with line-level evidence, is [portkit-integration.md](portkit-integration.md). Its decisions, adopted here:

- `git subtree add` of portkit (public history, one author, no Everydom material) under `crates/portkit/`, keeping the `portkit-*` crate names: `core`, `mcp`, `port`, `cli`, `plugin`, `read`, `index`. Dropped: `demo/`, `schema/` (Fellwork fixtures and vendored code), the Python example and the Python CI script.
- One `cowproof` package installs three binaries: `cowproof`, plus `pk` and `pk-read`, which Claude Code hooks and builder shells call by name. `cowproof pk ...` is the same command tree.
- The builder's `ask` / `check_ruling` / `run_check` and the director's `rule` / `watch` tools are portkit `Tool` implementations served by portkit's MCP server from the `cowproof` binary, which gives each one a CLI and MCP surface and a parity test.
- portkit is code-neutral already (`pk port capture` runs any command through `sh -c`); what is Python-specific is documentation, examples and CI, listed for rewording (portkit-integration.md, section 6.5).
- Known portkit fixes before lanes rely on it: the compaction watermark is written where `pk-read` never reads it (G5, a real bug), and the trace directory is cwd-relative and would land in a builder's patch (G6). The full list is G1 to G15.

It has two jobs:

1. **Porting harness.** `pk port capture --cmd <command>` accepts any command that speaks portkit's one-JSON-request-on-stdin, one-JSON-result-on-stdout contract, so a function-level Node adapter exposes each pure unit of the Everydom runner (header parsing, globs and ownership, append-only, status taxonomy, sandbox builders and more; 16 steps in portkit-integration.md, section 2) to capture. The reference runner and its adapter live in this repository under `reference/node-runner/` (covered by provenance.md), so capture needs no private checkout. The fixtures are committed, and each Rust replacement must pass `pk port replay` against them. Deliberate differences become scoped `accepted` entries with written reasons. Effectful units (cloning, spawning, sandbox launch, signals, port allocation) don't fit a JSON-to-JSON contract; they are proven by translated versions of the runner's existing test suites, recorded effect traces against fake executors, and golden sandbox profiles. The unit-by-unit split is in portkit-integration.md. The same mechanism gives users a **port packet**: a builder ports a script to a Rust CLI, and `pk port replay` is its proof gate.

   **Polyglot** (scope: the first release ships the `kind: port` packet, its lint rules and replay gate, and function-level adapters for Node/TypeScript and Python; whole-process capture for shell and other languages, which needs a new `pk port exec` mode, comes after the first release, Linux first, because pinning the clock for macOS system binaries is blocked by System Integrity Protection). Each source language gets a capture adapter that makes the original speak the contract without restructuring it: function-level shims for Python and Node/TypeScript modules, and whole-process capture for shell scripts, where the input is argv, environment, stdin and starting files, and the output is stdout, stderr, exit status and file effects. Adapters pin what makes runs differ (clock, randomness, environment, working directory, temp paths, locale) and run captures inside the lane sandbox. A port packet names its source language and adapter, lint checks that the adapter exists and the cases file is present, the parity report goes into the capsule, and a builder that cannot reach parity on a case escalates with the diff; only a director ruling turns it into an `accepted` difference. The runner's own Node-to-Rust port is the first worked example. Adapter details and what in portkit is Python-specific today are in portkit-integration.md.
2. **Usage monitor.** Each Claude builder lane gets portkit's hooks (`post-tool-use`, `user-prompt-submit`, `session-end`) in its cowproof-supplied settings, a lane-local `PORTKIT_STATE_DIR`, the `pk-read` and symbol tools to cut re-reads, and `pk doctor` as a preflight; if the preflight fails the lane still runs but is marked `untraced`. Trace totals roll into the summary, the capsule and the watch view.

Efficiency metrics, per lane and per wave: estimated cost per **accepted** patch; escalations and reassigns per lane by model; parked time and resumed-turn input tokens; tokens per changed line; context bytes delivered and saved; re-read rate.

### Auth and cost

Verified against Claude Code documentation on 2026-10-09:

- **API key** (`auth = "api-key"`): `ANTHROPIC_API_KEY` or `apiKeyHelper`, always used in `-p` mode. Builders run with `--bare`; cowproof supplies its own settings and tools with `--settings` and `--mcp-config`. The supported path in the first release.
- **Subscription** (`auth = "subscription"`): the user runs `claude setup-token` (documented for "CI pipelines, scripts") and exports `CLAUDE_CODE_OAUTH_TOKEN`. `--bare` does not read that token, so subscription builders get a lane-private `CLAUDE_CONFIG_DIR` and the clone clean-up described under Trust boundaries. Ships in the first release, documented as experimental.
- The runner caps concurrent builders per auth mode (`[limits]` in `cowproof.toml`; defaults 6 for API keys, 2 for subscriptions) and backs off on rate-limit errors. The docs don't state concurrency limits for subscriptions.

### Architecture

A Rust workspace. The six `lanes-*` crates were ported on 2026-10-09 as `cowproof-core`, `-cli`, `-host`, `-lint`, `-plan` and `-report` (54 tests passing); `-report` becomes `cowproof-prove`. Where the Rust crates lag the Node runner (supervision, status taxonomy, slot probing), the port follows Node, per portkit-integration.md, section 1.4.

| --- | --- | --- |
| `portkit-core`, `-mcp`, `-port`, `-cli`, `-plugin`, `-read`, `-index` (under `crates/portkit/`) | `srmcguirt/portkit` | tool registry and MCP server, parity harness, usage tracing, `pk-read`, symbol index |

Per-repository `cowproof.toml`:

```toml
[roles]
director = "claude:opus"
```

### R2-1 — completeness (blocking)

**Problem**

> `run_check` has the runner, which runs outside the sandbox, execute a check command against the builder's clone. During the run the builder controls everything in that clone, including test configuration, build and package scripts and any file the check command calls. The protected-path gate only fires later, at handback. If the runner executes the check with its own privileges, the builder gets arbitrary code execution outside the sandbox. That code can write the control directory (forging rulings and records, which defeats the Trust boundaries section), reach the real tree, and use the network and credentials the runner holds. The only constraint stated is 'check commands have no network at all', which does not say they are sandboxed.

**Remedy**

> State that `run_check` executes the check inside a sandbox with the lane's filesystem policy or a stricter one: write access to the clone and scratch only, no read or write access to `lane/control/` or the real tree, no credentials and no network. The runner records only the exit status it observes. Treat check execution as untrusted code in the threat model.

### R2-2 — completeness (blocking)

**Problem**

> R1-10's obligation, keeping the credential from being exfiltrated, is still unmet, and the new mitigation rests on an unsupported claim. The credential stays readable by builder commands, and the design says the network allowlist bounds where it can go. But the allowed hosts accept authenticated writes under any caller's credential. Hostile repository content can supply an attacker's own key, and a builder can then upload the victim's key or OAuth token to the model provider API under the attacker's account (for example the Anthropic Files API, or an OpenRouter account) and read it back later. With `"network": "registries"` it can also publish to a public package registry. A spend-capped API key limits the damage only in API-key mode. A subscription OAuth token has no spend cap and grants the user's account.

**Remedy**

> Either keep the credential in the egress proxy for the first release (the proxy injects the lane's credential and rejects or strips any other `Authorization` or `x-api-key` header, which needs TLS termination for provider hosts), or restrict what the proxy forwards to the provider endpoints the builder runtime needs and to read-only registry fetches. Otherwise state the residual risk accurately: allowed hosts are exfiltration channels. Also say whether subscription mode, whose token cannot be spend-capped, is acceptable under that risk.
