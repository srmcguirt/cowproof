## Remote hosts (D27)

First slice of the remote side, the hidden `cowproof host-agent` verbs that need no sockets: `prepare`, `patch`, `doctor` and `cleanup` (`crates/cowproof-cli/src/host_agent.rs`). Each prints one JSON object (`{"ok": true, ...}` or `{"ok": false, "error": "..."}`) and exits 0 or 1. The one exception is `patch`: on success it prints the raw patch bytes, because a patch need not be UTF-8 and JSON would change it; a failure is still the JSON error and exit 1. The lanes root is `--root`, default `~/.cache/cowproof/remote-lanes`.

Done, and exercised by `tests/host_agent.rs` (real binary, everything under `/var/tmp`) and two unit tests:

- **`prepare --lane-id <id> --base <sha> --director-version <v> [--base-patch <file>]`** reads a git bundle from stdin. It makes a throwaway source repository from the bundle, checks out `<sha>`, applies the base patch there as uncommitted work, and hands that repository to the local runner's own `prepare_lane`. So the layout (`clone`, `home`, `scratch`, `control`, `sock` at 0700), the isolated clone with no remote or alternates, `base.patch` committed under the launch baseline, the removal of `.env` and `CLAUDE.md`, and `control/lane.json` are the code a local lane uses; there is no second clone implementation. It refuses an existing lane (left untouched), a version that differs from this binary's (both are named), an id outside `[A-Za-z0-9._-]{1,64}`, a `--base` that is not a full commit id, and a bundle that does not contain the commit. A refusal leaves no lane and no throwaway directory.
- **`patch --lane-id <id>`** finds the launch commit in `control/lane.json` and runs the runner's own `capture_patch` (git inside the check sandbox, since the builder owns the clone's `.git`). A unit test compares its bytes with a direct `capture_patch` call on the same tree; an integration test applies the output with `git apply` to a fresh clone of the base and compares it with git's own output for the same command line (binary file, new file, deletion included). A link at `<root>/<id>` is refused.
- **`doctor [--claude-bin <name>]`** runs the preflight and reports its `sandbox` and `claude` checks: `{"ok", "version", "claude", "claude_detail", "sandbox", "sandbox_detail"}`. `ok` means both pass (exit 1 otherwise). The API key is deliberately not checked: a remote host must not have one (D27).
- **`cleanup --lane-id <id>`** removes `<root>/<id>`. It is idempotent, refuses ids that could leave the root, unlinks a symlink planted at `<root>/<id>` without touching its target, and refuses a plain file.

Two small changes outside the new module: `LaneLayout::for_lane_dir` and a public `validate_lane_id` in `cowproof-run` (the layout is now named in one place, and `prepare_lane` uses it), and `capture_patch` in `run.rs` is `pub(crate)` so the remote verb can call it instead of copying it.

### `builder` and `check` (second slice)

Both verbs read ONE JSON spec on stdin and run only in a lane that `prepare` made. Neither shares an implementation with the local runner: `Launcher::launch` and `run_declared_check` in `run.rs` now call the same `write_lane_files`, `builder_command` and `run_check_command` that `host-agent` calls. The local run's behavior is unchanged (the `run`, `slots`, `doctor` and `deps` suites pass as before).

- **`builder --lane-id <id> [--root <dir>]`** takes the launch spec (`model`, `prompt`, `system_prompt`, `settings`, `resume_session_id`, `placeholder_key`, `bridge_port`, `port_base`, `max_turns`, `claude_bin`; any other field is refused). It writes `settings.json`, `mcp.json` and `system-prompt.md` into the remote lane's `home/` with `write_lane_files`; `mcp.json` names `cowproof lane-tools --socket <root>/<id>/sock/runner.sock` and is not part of the spec, because its only content is this host's two paths. It then runs the builder through `builder_command`: the bridge wrapper, then `claude`, under the same builder sandbox policy and the same environment (`HOME`, `CLAUDE_CONFIG_DIR`, `TMPDIR`, `CLAUDE_CODE_TMPDIR`, `COWPROOF_RUNNER_SOCKET`, `COWPROOF_PORT_BASE`, `PORTKIT_*`). The base URL is `http://127.0.0.1:<bridge_port>`, and `bridge_port` must be the lane id's `bridge_port` (D24).
  - **Streams.** The builder's stdout is this process's stdout, byte for byte (the SSH channel back to the director's stream pump). Its stderr goes through the runner's own `pump_stderr` into `control/builder.stderr`, redacted. The exit code is the builder's. SIGINT, SIGTERM or SIGHUP (what a closed SSH channel sends) end the builder's whole process group, SIGTERM first and SIGKILL after the local grace, and the verb exits 130; when the leader exits by itself, whatever it left in the group is killed at once, as locally.
  - **Sockets.** `<root>/<id>/proxy.sock` and `sock/runner.sock` must already exist as sockets (the director forwards them with `ssh -R`, D24); otherwise the verb refuses before starting anything and says so, because the Linux policy binds a socket only when the file exists.
  - **No key.** The spec is scanned before it is parsed: a key named like a credential (`api_key`, `auth_token`, `secret`, `password`, ...) or a string the redactor would change (an `sk-` token, a JWT, `ghp_`, `xox`, `OPENROUTER_API_KEY=`) refuses it with exit 1 and names only the place in the JSON, never the value. The two free-text fields (`prompt`, `system_prompt`) skip only the `Bearer` rule, so a packet that explains HTTP auth is not refused. The refusal comes before any lane file is written.
  - **The placeholder.** The builder's `ANTHROPIC_API_KEY` is the lane's `placeholder-...` value, not a real key: the director's proxy refuses a request that does not present its own placeholder, so the spec has to carry it. `placeholder_key` must start with `placeholder-`. The real key is never in the spec or in the builder's environment (the test runs host-agent with a real-looking key in its own environment and checks the builder's environment for it).
  - **Not in the spec.** The wall-clock and cost limits stay on the director: it meters the stream and ends the SSH command. `--unsandboxed` does not exist on the remote.
- **`check --lane-id <id> --check-id <id> [--root <dir>]`** takes `{command, timeout_secs, port_base?}` (`timeout_secs` at most the local 20 minutes) and runs the command with `run_check_command`, the function the local `run_check` tool calls: `sh -c` in the clone, in the check sandbox. It prints `{ok, exit_code, timed_out, output_tail}`: `ok` is a zero exit that did not time out, `exit_code` is -1 for a timeout, and `output_tail` is the output redacted whole and then cut to its last 32 KiB (the local cap) with a marker when cut. It exits 0 whenever the check ran, pass or fail, and 1 with the JSON error only when it could not be run (a spec that holds a key, a bad spec, no such lane). A failed check is a result, not a refusal.

Tests: `tests/host_agent.rs` drives the real binary (a copy outside the home) under `COWPROOF_REQUIRE_SANDBOX=1` against a fake `claude`: stdout byte for byte (with bytes that are not UTF-8 and no final newline), the exit code, the lane files and the `mcp.json` socket, the environment (bridge URL, placeholder, no real key), the clone writable and a write outside it denied, redacted stderr, six shapes of a spec that holds a key, nine launches that do not fit the lane, SIGTERM ending the fake and a background child that ignores SIGTERM (by a marker file that stops growing and a dead pid), a builder that ignores SIGTERM being killed after the grace, and the `check` cases (exit codes, sandbox, redaction, cap, timeout, refusals).

Still open: nothing here has run against the real WSL host or over a real `ssh -R`; the hook commands in `settings` name a `pk` path, and the sandbox grants execution only of the `pk` beside this host's `cowproof`, so a director that sends hooks must point them at that file; `check` serializes nothing (two concurrent checks in one lane would race on `control/run_check.sb`, so the director keeps its one-at-a-time rule); and a timed-out check kills its shell but not a grandchild, as the local `run_check` does today.

### Director side: `cowproof run --host <alias>` (lane/run-host)

The third slice: the director's half of D27. `crates/cowproof-cli/src/remote.rs` is the SSH transport, `run.rs` has the remote branch (`Launcher::launch`, `run_declared_check`, the patch, the end of the lane), `main.rs` has `--host` and the hosts config, and the capsule has a sealed `host` field (`#[serde(default)]`, null for a local lane). `README.md` has "Run a lane on another machine".

- **Order.** Local preparation as before (clone, slots, proxy, runner socket, director socket); then one control master (`ssh -M -S <lane>/control/ssh.ctl -o ControlPersist=no -o StreamLocalBindUnlink=yes -o ExitOnForwardFailure=yes -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=4 -N <target>`); `host-agent doctor` (a failure is exit 4, run.json `infrastructure`, nothing prepared); `prepare` with a bundle on stdin; the two `-O forward -R` requests, after `prepare` made the remote lane directory; `builder` with the spec on stdin, its stdout into the unchanged stream pump and meter; `check` for every `run_check`; `patch`; `cleanup`; `-O exit`. `Drop` and the post-builder signal task run the same cleanup, so an error path or a late signal still removes the host's lane and stops the master. Every ssh argv comes from one function, `ssh_argv`, and every remote command from `agent_command` (each word shell-quoted, because ssh joins its arguments and the host's shell re-parses them); both are unit-tested.
- **The key.** The builder spec holds the lane's `placeholder_key`; the real key is moved into the proxy and nowhere else. The host's environment is whatever sshd gives a command, and the host-agent refuses a spec that holds a credential-shaped string as a second wall.
- **Hosts config.** One config, extended: each alias takes `cowproof`, `claude` and `remoteRoot` beside `ssh`. Lookup order: `COWPROOF_HOSTS_FILE`, `LANES_HOSTS_FILE`, `~/.config/cowproof/hosts.json`, then the old `./hosts.json` (then `hosts.example.json`, which does not exist in this repository). The working-directory `hosts.json` is kept because `cowproof plan` and `cowproof hosts` read it (`configured_hosts`); nothing in the repository's docs or tests names it. It comes after the user file on purpose: a `hosts.json` that arrives with a checked-out repository must not choose the machine a remote lane runs on, nor the command it runs there. A destination that starts with `-` (ssh would read it as an option) is refused.
- **Tests.** `tests/remote.rs` drives the real `cowproof` (a copy outside the home) twice over: as the director and, through a fake `ssh` (`tests/common/fake_ssh.py`, python3), as the host-agent on a fresh environment. The fake logs every argv and every stdin, emulates the control master, `-O check|forward|exit`, runs commands through `sh -c` joined like sshd does, and forwards a termination as SIGHUP to the command's group (a pty hangup). Fourteen tests: a proved run (patch back, proof local, capsule `host`), the step order and that each goes through the one master, the forwards after `prepare`, no real key in any argv, any stdin or any file under the host's root and home (the fake reads them all just before `cleanup`), the placeholder in the builder's environment, a failing doctor, SIGINT during the builder (exit 130, host-agent, builder and background child gone, lane removed, master stopped), a wall-clock timeout (exit 5), a refuted run (exit 2, lane removed), `run_check` seeing the host's tree, and the config and flag errors.

Findings, with a recommendation for each:

1. **The forwarded socket must be a socket.** `host-agent builder` checks `symlink_metadata(...).is_socket()`, so a symlink standing in for `ssh -R` fails it. The fake therefore listens on a real Unix socket and relays to the director's (a few lines of python), which is what a real forward gives. No change needed.
2. **SIGHUP is only sent with a pty.** The builder's ssh runs without a terminal (a pty would turn `\n` into `\r\n` in the stream and cap stdin lines at 4096 bytes). Killing the local `ssh` closes the channel, but sshd does not signal a command that has no pty: the remote `host-agent builder` ends when it next writes to the closed pipe (SIGPIPE), or when the lane directory is removed, not at once. The fake delivers SIGHUP, as the brief says a real host does, so the tests do not prove the real behaviour. Recommend, in `host_agent.rs`: have `drive_builder` also end the group when its stdout pipe breaks or its parent changes, and when `proxy.sock` disappears; and check it in the live test by killing the director mid-builder.
3. **`prepare --base-patch <file>` takes a path on the host, and no verb sends a file.** So `--allow-dirty` is refused with `--host` (a remote lane starts from a commit). Recommend: `prepare` reads the base patch from stdin after the bundle, with a byte count in an option.
4. **`git bundle create - <sha>` refuses a bare object name** (it needs a ref and says "Refusing to create empty bundle"). The director bundles `HEAD`, after checking `HEAD` is still the lane's base. A repository whose HEAD moves during the run fails the lane (exit 4) instead of sending the wrong base.
5. **The builder's stderr stays on the host.** Only ssh's own stderr and `host-agent`'s messages reach the director's `builder.stderr`; the builder's, kept in the host's `control/builder.stderr`, is removed with the lane. Recommend a `host-agent` verb that prints it, fetched before `cleanup`.
6. **No portkit hooks.** The settings sent are `builder_settings(None)`, so a remote lane is `untraced` with that reason in `run.json`.
7. **Local `claude` is not needed.** With `--host` a failing local `claude` preflight check is printed as a note, not a failure; the host's doctor checks its own.
8. **The host and the director must agree on the launch baseline.** `prepare` returns the files it removed; the director compares them with its own `launch_removed` and stops (exit 4) on a difference, because the returned patch would not apply to the tree the proof rebuilds.

Still open: nothing here has run over a real `ssh`; the control path must fit in a Unix socket path (the director refuses a longer one, with the 17 characters ssh adds); a real master can survive a hard kill of the director (`ServerAliveInterval` ends it once the link drops).

## Seal bypass in `verify`, found and fixed (2026-10-11)

The AppleDouble failure above had a real cause. `Capsule::read` checked the seal and every file `capsule.json` lists, but `verify` then loaded every `*.json` in `checks/` by listing the directory, and ran each one's `command`. A file added to a sealed capsule was therefore run while the seal still passed. The macOS `._` file only failed because it was not UTF-8. An unlisted top-level `base.patch` was applied the same way.

V-1 (Sonnet) fixed both:
- checks are loaded only from the sealed `file_hashes` keys;
- `Capsule::read` refuses any entry in `packets/`, `checks/` or `applied/` and any top-level capsule file that the seal does not list (new `UnsealedFile`, exit 4, naming the path, with a `COPYFILE_DISABLE=1` hint for `._` names).

The attack test failed on the old code with the marker file written ("the unsealed check ran"). The director's own mutation, accepting every entry, failed the end-to-end CLI test. Gate: 1122 passed, 0 failed. A forger who rewrites both `capsule.json` and its seal is still out of scope until capsules are signed.

## R-5 and R-6: orphans swept, and a Linux-only defect (2026-10-11)

**R-5** (`9602b5a`):
- the host records its builder's process group and ends any live one, checked by pid and start time, before `patch`, `cleanup` or a relaunch;
- every `cowproof run --host` first sweeps lanes whose director is gone: it stops their master and removes the host lane, and keeps the local lane as evidence, marked `swept`.

Live, a director SIGKILLed mid-builder, then a new run: the orphan's master was stopped, the host lane removed, and the new lane proved.

The sweep line said the builder group was "unverified", for a group that was long gone. The cause: the host-side checks shelled out to `/bin/sh -c 'kill -0 -- …'`. On Ubuntu `/bin/sh` is dash, and dash's `kill` rejects `--` ("Illegal number: -"). So on Linux:
- every process and group read as alive;
- a dead leader read as unknown;
- a live group got SIGTERM but never the SIGKILL;
- single-process signals never went out.

Ubuntu CI failed three unit tests on `9602b5a`, and its integration tests never ran, because the failing binary stopped the job. macOS passed because its `/bin/sh` is bash. The gate now has a Linux leg: the lane's HEAD is sent to the Linux host as a git bundle, and the whole workspace runs there with `--no-fail-fast`. It reproduced CI's three failures on `9602b5a`.

**R-6** (`97efff4`, Sonnet) moved the checks to `kill(2)` in `cowproof-prove`, with ESRCH meaning gone and EPERM meaning present. The director added three things:
- process groups 0 and 1 are refused before `kill(2)`, because `kill(-1, ..)` reaches every process the user may signal;
- the test helper `group_gone`, which had the same dash defect, also uses `kill(2)`;
- one test expectation became macOS-only. On Linux the builder runs in bwrap's pid namespace, so SIGTERM ends bwrap and the kernel kills the whole namespace. A child that ignores SIGTERM therefore needs no SIGKILL there.

Gates: macOS 1152 passed, Linux 1148 passed, 0 failed. Live after R-6:
- the remote builder was gone one second after a director SIGKILL;
- the host removed its own group record;
- the next run swept the orphan with "master stopped, host lane removed";
- no master and no host lane was left.
