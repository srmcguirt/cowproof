- **Dependency prefetch (D6, D11, D14, F-1): done for Cargo (2026-10-10, audit blocker 5).**
  - **Flow.** Before verify runs, `cowproof run` rebuilds the tree (base commit, `base.patch`, launch baseline, `lane.patch`), computes `dependency_cache_key` on it and looks in `<cache root>/deps/<key>/`. The cache root is `~/.cache/cowproof`, or `$COWPROOF_CACHE_ROOT` (the override tests use). A miss runs `cargo fetch --locked` in a private work directory under the cache root and renames it into place, so no concurrent lane sees half an entry; a lane that loses the rename race reports `hit`. The capsule records the key and the outcome (`hit`, `fetched`, `failed`) in `capsule.json`, which the seal covers. `cowproof verify` does the same from the capsule's key (it fetches when its own cache root lacks the entry) and refuses a rebuilt tree whose key differs.
  - **The fetch sandbox** (`SandboxPolicy::dependency_fetch`) writes only its own work directory and reads the rebuilt tree, the toolchain and the one `cargo` executable. Its environment is `PATH`, `CARGO_HOME`, `RUSTUP_HOME` and `HOME`; it holds no key, cannot see the lane's control directory, the other lanes or the real home, and `cargo fetch` runs no `build.rs` or procedural macro. **Its network is the one knob: `COWPROOF_FETCH_NETWORK`, `open` by default (full outbound network) or `none`.** The default is `open` because the registry-only egress filter (`NetworkMode::RegistryReadOnly` through the proxy) does not exist, and a no-network default would fail every real project. The tests use `none` with a registry on disk.
  - **Registry configuration comes from the base only.** The key and the fetch read `.cargo/config.toml`, `.cargo/config`, `.npmrc` and `.yarnrc*` as the tree had them before `lane.patch` (`RegistryConfigSnapshot`), and the protected-paths gate (one list, `cowproof_run::REGISTRY_CONFIGS`, root and nested) refuses a lane patch that touches them unless the packet owns the path.
  - **The mount.** The verifier's `CARGO_HOME` stays private and writable (its package lock, config); only `registry/` and `git/` are the cache's, linked in and granted READ-ONLY, and checks run with `CARGO_NET_OFFLINE=true`. A read-only grant now also denies writes on macOS (`(allow default)` allowed them outside the home); on Linux the whole filesystem was read-only already.
  - **F-1.** A failed fetch (or one that could not start) is `infrastructure`, exit 4, "dependency fetch (cargo fetch --locked) failed: ...", and verify is not run. Never `refuted`.
  - Open:
    - **npm, yarn, pnpm and Bundler are not fetched.** The cache key already hashes their lockfiles and registry config, but no fetch adapter exists, so a tree without a `Cargo.lock` records no dependency key or outcome and a check that needs `node_modules` fails offline in verify (and is judged `refuted`, which F-1 says it should not be). An npm adapter (`npm ci --ignore-scripts` in the same sandbox) needs an offline fixture (a local registry or a packed tarball) before it can be claimed.
    - **A registry-only egress filter for the fetch** (replace `open`): the proxy would need a registry allowlist. Until then a fetch that reads a lockfile the packet owns (a git dependency, say) can reach any host, with nothing secret in reach.
    - **A packet that owns a registry config file** passes the gate with a warning, the fetch and the key use the base's file, and the verifier's tree has the patched one. A check that depends on the patched config may diverge in verify. Decide whether those paths can be owned at all.
    - **A cargo reached through a `rustup` proxy under the real home** is granted as an executable and given `RUSTUP_HOME`, but that path (a hidden real home) has only run here with the toolchain's own `cargo` (`$CARGO`), not the proxy.

    - `cargo fetch` unpacks crates into `registry/src`, which is what lets the read-only mount work; a project whose build needs something else written under `registry/` (a registry the fetch did not touch) would fail in the verifier, and that failure is a `diverged` check, not infrastructure.

- **Lane endpoints and the in-sandbox bridge (D24): done (2026-10-10).** The proxy is `<lane>/proxy.sock` (mode 0600) on macOS and Linux. `cowproof net-bridge --port <P> --target <sock>` (hidden) binds `127.0.0.1:<P>` only, prints `READY` on stderr, relays bytes both ways to a fresh `UnixStream` per connection, allows 64 at once and logs nothing. With `-- <argv>` it starts that bridge as a child, waits up to 5 s for `READY`, then execs the command in place (argv only, no shell), so claude is the sandbox's own process and its exit status is the process's; the bridge exits within about 25 ms of its parent going away. `cowproof run` launches the builder that way. P is `40000 + FNV-1a(lane id) % 17000` (`bridge_port`; it was `% 20000` until C6-R1 moved the range below the port blocks), recorded in `run.json` as `bridgePort`. macOS: Seatbelt allows bind, inbound and outbound on `localhost:<P>` only, plus the exact-path connect to `proxy.sock`. Linux: `--unshare-net` stays and `proxy.sock` is bound in by itself; bubblewrap brings `lo` up in the namespace, so the bridge binds there (checked in a Linux container: `lo` came up and a 127.0.0.1 bind and connect worked under `--unshare-net`; it needs `CAP_NET_ADMIN` in a container, a plain runner has it). Open: (1) two lanes whose ids hash to one port, or a host service on P, make the second builder fail to start (the bridge retries the bind for 3 s, then the wrapper refuses to run claude); this is a safe failure, but on macOS the sandbox shares the host's loopback, so a few lanes with colliding ids cannot run at once. Linux lanes have their own namespace and never collide. The cli `run` test harness therefore picks lane ids whose bridge ports are distinct and free (about 40 parallel harnesses would otherwise collide by chance a few percent of runs). (2) The cli e2e sends a request the real proxy refuses (403), because the runner's upstream is a constant and a stub socket swapped in over `proxy.sock` would race the sandbox's bind of the socket on Linux. A happy-path request through the real proxy to a fake upstream needs an upstream override that does not exist (and must not be an environment variable, which would redirect the real key). (3) The live tests build `cowproof` with a nested `cargo build -p cowproof-cli --locked` because the `cowproof-run` test binary cannot name another package's binary.
